## Objective

Replace every hardcoded brand hex value in `src/` with the tokens defined in
W38.1.1, and in doing so fix the three-reds / two-navies inconsistency so the
site reads as one brand instead of four near-misses.

## Background

W38.1.1 built the palette. Nothing consumes it yet. This spec is the payoff:
after it lands, changing TSA's crimson is a one-line edit in `index.css` instead
of a find-and-replace across eight files that misses one.

The real win is not tidiness. Right now `#ED1C24` (a bright fire-engine red) sits
in the slide-out menu and a background blob, while `#9B1B30` (a deep crimson)
sits on the buttons two sections below. A visitor scrolling past sees two
different brands. That's the bug you're fixing.

## Specification

1. **Find every occurrence.** Search `src/` for `#` followed by hex digits.
   Include `.tsx`, `.ts` and `.css`, and check 3-digit hex (`#fff`) as well as
   6-digit. Build the list before you change anything.

   For calibration, a `grep -roE "#[0-9A-Fa-f]{6}" src/` today returns **66
   occurrences of 23 distinct values**, concentrated here:

   | File | Count |
   | --- | --- |
   | `BoardMembersSection.tsx` | 24 |
   | `aero-hero-2.tsx` | 12 |
   | `HomePage.tsx` | 6 |
   | `StaggeredMenu.tsx` / `.css` | 10 |
   | `AboutUsScroll.tsx` | 4 |
   | everything else | 10 |

   Not all 66 are in scope — see steps 5 and 6.

2. **Map each one.** Use this table. Where two hexes collapse to one token, that
   collapse *is* the fix:

   | Current | Replace with | Note |
   | --- | --- | --- |
   | `#9B1B30` | crimson (`--tsa-red-600`) | primary red |
   | `#7A1028` | `--tsa-red-700` | hover partner |
   | `#A51931` | `--tsa-red-500` | flag red |
   | `#ED1C24` | `--tsa-red-500` | **behavior change — see step 3** |
   | `#241D4F` | `--tsa-navy-700` | |
   | `#2D2A4A` | `--tsa-navy-500` | |
   | `#E8C547` | `--tsa-gold-500` | |
   | `#FFFFF0` | `--tsa-cream-100` | |
   | `#F4F5F8` | `--tsa-cream-100` | near-white name tag — collapse it |
   | `#141414` | `--tsa-navy-900` | gallery background; **coordinate with Track D** |
   | `#f0ebe6` | `--tsa-sand-100` | already the background token |
   | `#1C2B5A` | `--tsa-navy-500` | a *fourth* navy, hiding in the hero avatar fallback text |

   `#1C2B5A` is easy to miss — it appears once, on the `AvatarFallback` in
   `aero-hero-2.tsx`, and it's a navy nobody else uses. Fold it in.

3. **The `#ED1C24` change is the one visible change in this PR.** It appears in
   two places: the `colors` prop on `StaggeredMenu` in `HomePage.tsx`, and the
   fill of the left background blob in `BoardMembersSection.tsx`. Both become the
   deeper flag red. Screenshot both before and after and put them in the PR —
   this is the change a reviewer should actually look at.

4. **Prefer utility classes over inline styles** where the surrounding code
   already uses Tailwind. `bg-[#241D4F]` becomes `bg-tsa-navy-700`, not
   `bg-[var(--tsa-navy-700)]`. Arbitrary-value syntax with a var in it works, but
   it defeats the point of registering the tokens in `@theme`.

5. **`StaggeredMenu` has leftover template colors — understand them before you
   touch them.** That component ships with default prop values
   (`colors = ["#B497CF", "#5227FF"]`, `accentColor = "#5227FF"`) and CSS
   fallbacks (`var(--sm-accent, #ff0000)`, `var(--sm-accent, #5227ff)`) left over
   from the template it came from. Purple and pure red are nowhere near TSA's
   brand.

   **They don't currently render** — `HomePage.tsx` passes real props that
   override every one. But they are a loaded gun: drop a prop in a future refactor
   and purple appears in the nav. Update the defaults and the CSS fallbacks to
   brand values so the component is safe on its own. This is a small change with
   real value; a reviewer should ask about it.

6. **Some values must stay as strings.** `StaggeredMenu` takes `colors` and
   `accentColor` as props and passes them to GSAP, which cannot read a CSS
   custom property name. Two options — pick one and say which in your PR:
   - keep literal hex there, but import it from a small shared TS constants
     module so it's still single-sourced; or
   - read the computed custom property at runtime with
     `getComputedStyle(document.documentElement).getPropertyValue(...)`.

   The first is simpler and probably right for this codebase. Don't gold-plate it.

7. **Leave non-brand colors alone.** Tailwind's `zinc-*`, `white/10`,
   `black/45`, `rgba(0,0,0,0.55)` in shadows, and the `oklch` status colors are
   all fine. This spec is about *brand* colors. Converting greys to tokens is
   scope creep and makes the diff unreviewable.

8. **Delete `src/App.css`.** It is the unmodified Vite starter stylesheet — it
   styles a `.logo` class that spins, a `.card`, and a `.read-the-docs` class,
   none of which exist in this project. Confirm with a repo-wide search that
   nothing imports it (`App.tsx` does not), then delete the file. If something
   does import it, leave it and say so in the PR.

## Out of Scope

- Redesigning anything — this is a swap, not a restyle

- Fonts

## Hints

- Do this file by file and commit per file. If a conflict lands, you lose one
  file's worth of work instead of the whole PR.
- `grep -rn "#[0-9A-Fa-f]\{6\}" src/` is a fast way to build the list. Also check
  for 3-digit hex (`#fff`).
- The board name tag logic currently reads
  `(tagColor === "#2D2A4A" || tagColor === "#A51931") ? "text-white" : "text-zinc-900"`.
  That's a string comparison against hex literals — it will silently break if you
  change the values without changing the comparison. Worth thinking about whether
  the data should carry a `textColor` rather than the component inferring one.
- Tailwind v4 generates utilities from `@theme` tokens at build time. If
  `bg-tsa-navy-700` doesn't work, the token probably landed in the wrong block in
  W38.1.1 — go talk to whoever wrote it rather than falling back to arbitrary values.
