## Objective

Turn the gallery from nine unlabeled images into a record of TSA's events —
each photo tied to the event it came from — and make the page usable with a
screen reader.

## Background

The gallery is a hardcoded array of nine paths and every single `<img>` has
`alt=""`. To a screen reader user, this page is **completely empty**. They arrive
and there is nothing there.

To a sighted visitor it's not much better: nine photos with no indication of what
event any of them is from. TSA runs Songkran, Loy Krathong, Thai Trivia Night,
dessert fundraisers, movie nights, mixers with other Asian student orgs, and a
spring picnic. A photo from Songkran and a photo from a boba fundraiser look
completely different and mean completely different things — the page throws that
information away.

TSA asked for "a gallery for all events" and "an archive of previous events." A
flat list of files can't grow into either.

## Files You'll Touch

```
src/pages/GalleryPage.tsx    modify
src/data/gallery.ts          create (optional but recommended — see step 1)
```

## Specification

1. **Give each image a real data shape.** Replace the flat `IMAGES` array with
   objects carrying at minimum:

   | Field | Notes |
   | --- | --- |
   | `src` | Filename only. Let the component prepend `import.meta.env.BASE_URL` — same reasoning as the board data in W38.3.1. |
   | `alt` | Descriptive. Required. |
   | `event` | Which event this is from. |
   | `date` or `term` | Enough to sort and, later, to archive by. |
   | `caption` | Optional display text. |

   Putting this in `src/data/gallery.ts` mirrors what Track C did for board
   members and is the better long-term shape. Keeping it in the page file is
   acceptable if you're short on time — say which you did and why.

2. **Write real alt text for all nine images.** Describe what is in the photo,
   for someone who cannot see it. "Students releasing krathong lanterns on the
   campus pond at night" — not "gallery image" and not "TSA event."

   Where you genuinely don't know what an image shows, say so in the PR and use
   the most accurate description you can from looking at it. Don't guess at event
   names.

3. **Show captions on the tiles.** Event name at minimum. Match whatever surface
   W38.4.1 chose — if the page went light, a caption below the image is natural;
   if dark, an overlay at the bottom of the tile works. Captions must not hide
   the photo.

4. **Group by event, or make grouping possible.** Either implement visible
   grouping (a heading per event, tiles beneath) or structure the data and
   rendering so grouping is a small change later. If you don't implement it, say
   in the PR exactly what the next person needs to do.

5. **Three of the nine are video posters.** `water_festival_poster.jpg`,
   `krathong_poster.jpg` and `trivia_poster.jpg` are still frames generated from
   the MP4s in `public/video/` by `npm run extract-posters`. They're currently
   presented as ordinary photos, which is slightly dishonest — there's video
   behind them. Either mark them (a small play indicator) or note it for a future
   spec. Don't build a video player here.

6. **Keep the page fast.** Images already use `loading="lazy"`. Keep it. Adding
   captions must not defeat lazy loading — if you wrap tiles in a component that
   measures them, you can accidentally force all nine to load at once.

7. **Captions must not break the masonry.** The layout is CSS columns with
   `break-inside-avoid`. Adding text inside a tile changes its height and can
   cause a tile to split across a column boundary. Verify at all three
   breakpoints after adding captions.

8. **Add a count or context line** under the page heading — something like "27
   photos from 6 events" — so the page feels curated. Derive it from the data;
   don't hardcode a number that goes stale the moment someone adds a photo.

## Acceptance Criteria

- [ ] All nine images have descriptive, specific alt text — no `alt=""` anywhere on the page
- [ ] Each image carries event and date information in the data
- [ ] Captions are visible on tiles and don't obscure the photos
- [ ] Grouping is implemented, or the data supports it and the PR says what's left to do
- [ ] Video posters are either marked or explicitly noted for a follow-up
- [ ] `loading="lazy"` still works — verify in the devtools network tab that images below the fold don't load until you scroll
- [ ] Masonry doesn't break tiles across columns at 375px, 768px or 1440px
- [ ] The count line is derived from the data, not hardcoded
- [ ] **Screen reader check:** run the page through VoiceOver (macOS: <kbd>Cmd</kbd>+<kbd>F5</kbd>) or NVDA (Windows, free) and confirm every image is announced meaningfully. Note in the PR what you heard.

## Out of Scope

- Lightbox / full-screen viewer
- Adding new photos
- Playing video inline
- Filtering or search
- A paginated archive by year — noted in `features_TODO.md`

## Hints

- Good alt text answers "what would I say if I were describing this photo to
  someone on the phone?" Keep it under about 125 characters.
- Decorative images take `alt=""` — that's the correct use. These are content
  images, so they don't.
- If a caption already names the event in visible text, repeating it verbatim in
  the alt is redundant to a screen reader user, who hears both. Describe the
  *image* in the alt; name the *event* in the caption.
- `<figure>` and `<figcaption>` are the semantically correct elements for an
  image with a caption. Worth looking up before reaching for a `<div>`.
- Never used a screen reader? Budget ten minutes to try it. It's the single most
  useful hour of web development most students never spend, and this spec is a
  good excuse.
- Ask the club for event names before inventing them. A wrong event label on a
  public site is worse than a generic one.
