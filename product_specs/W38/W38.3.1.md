## Objective

Move board member information out of a hardcoded array inside a component and
into a typed data file, with the fields the design actually needs — so adding
next year's board is editing one list, not rewriting a component.

## Background

"Board Member Gallery" is the **first item** on TSA's feature request list, and
"Archive of Previous Board Members" is second. What exists today is a
14-entry `CARDS` array declared at the top of `BoardMembersSection.tsx`, where
each entry has: an image path, a CSS rotation string, a lowercase first name, and
a hex color.

There is no role. No major. No year. The section's own subheading admits it:

> A scattered "work-style" grid with inertia scroll. We'll swap these
> placeholders for real board photos + roles next.

Compare that to how TSA presents their board on Instagram: a card per person with
their **name**, **role** in large type down the side (President, Treasurer,
Senior Advisor, Graphics Coordinator, Public Relations, Graphic Designer, Alumni
Advisor), their **major** (Computer Engineering, Accounting & Finance, Physics &
Astronomy, Economics & Finance / History), plus **hobbies** and a favorite snack.
Their site shows a photo with a lowercase nickname and nothing else.

Two more things this spec has to reckon with:

- **Presentation data is mixed into content data.** Each entry carries `rotate`
  and `tagColor` — pure styling, sitting in what should be a content list. When
  the club adds a 15th member they shouldn't have to pick a hex code.
- **Fourteen photos, and we don't know who half of them are.** The public folder
  has `Alison.jpg`, `Ei.jpg`, `Linh.jpg`, `Ismail.jpg`, `Eric.jpg`,
  `Christina.jpg`, `Crystal.jpg`, `Gokul.jpg`, `Dara.jpg`, `Xander.jpg`,
  `Vincent.jpg`, `Ije.jpg`, `Pat.jpg`, `Im.jpg`. Roles for some are visible on
  TSA's Instagram; others we'd be guessing at.

## Specification

1. **Create `src/data/board.ts`** and export a `BoardMember` type plus a
   `BOARD_MEMBERS` array.

2. **Design the type around these fields:**

   | Field | Required | Notes |
   | --- | --- | --- |
   | `id` | yes | Stable slug, e.g. `"alison-wang"`. Use this as the React key, not the display name — names are not guaranteed unique. |
   | `name` | yes | Full display name. |
   | `nickname` | no | What the current tag shows. Several members go by one. |
   | `role` | yes | President, Treasurer, Public Relations, etc. |
   | `major` | no | |
   | `year` | no | Class year or grad year. |
   | `photo` | yes | Filename only — see step 4. |
   | `funFacts` | no | Short strings. W38.3.3 will use these. |
   | `term` | yes | e.g. `"2025-2026"`. **Do not skip this** — the archive feature needs it, and adding it later means editing every entry. |

   Add fields if the design needs them; justify each one in the PR. Every
   optional field is a field someone has to decide about later.

3. **Keep presentation out of the data.** `rotate` and `tagColor` should not be
   in `board.ts`. The scattered-grid rotation and the tag color are decisions the
   *component* makes. Derive them — from the index, or from a deterministic
   function of the `id` — so they stay stable across renders but aren't content.
   A stable pseudo-random from the id is nicer than index-based if members get
   reordered; either is acceptable, but say which you chose and why.

4. **Store the photo as a filename, not a full path.** Today each entry is
   built with `` `${base}Alison.jpg` ``, meaning `import.meta.env.BASE_URL` gets
   baked into the data. Keep the data as `"Alison.jpg"` and let the component
   prepend the base URL. Data files shouldn't know about deployment.

   This matters for GitHub Pages specifically — see the README section on
   referencing assets.

5. **Fill in what you can verify; mark the rest.** Cross-reference TSA's
   Instagram (`@umdtsa`) for roles and majors. For anyone you can't confirm, use
   a clearly provisional value and add a `TODO:` comment naming that person.
   **Do not invent a role for a real student.** Attributing the wrong title to a
   named person on a public website is worse than leaving it blank.

   List everyone still unverified in your PR description so the club lead can
   fill the gaps.

6. **Wire it up minimally.** `BoardMembersSection.tsx` should import
   `BOARD_MEMBERS` and render from it, producing the **same visual output as
   today**. Derive `rotate` and `tagColor` in the component; keep showing the
   nickname in the tag. This is a refactor, not a redesign — W38.3.2 does the
   redesign.

7. **Add a short comment at the top of `board.ts`** explaining how a future club
   member adds someone: drop the photo in `public/`, add an entry, done. Assume
   the reader is a first-year who has never seen this repo.

## Hints

- Deriving a stable value from a string id: a small hash of the id into an index,
  then index into an array of rotations. Deterministic, order-independent, no
  library needed. Keep it under ten lines.
- If you use `Math.random()` for rotation, cards will jump on every React
  re-render. This will look like a ghost bug and cost someone an hour. Don't.
- `as const` on the array gives you literal types; explicitly annotating
  `BoardMember[]` gives better errors when an entry is malformed. The second is
  usually more useful here — try both and see which error message you'd rather
  read at 1am.
- Photo filenames are capitalized (`Alison.jpg`, not `alison.jpg`). GitHub Pages
  is served from a **case-sensitive** filesystem. A wrong case works on Windows
  and macOS locally and 404s in production — this is a genuinely common way to
  ship a broken deploy. Copy the names exactly.
- Fourteen entries is a lot of typing. Doing it accurately *is* the hour.
