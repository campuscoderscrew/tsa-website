## Objective

Give the site one authoritative, named color palette in `src/index.css` that
encodes TSA's brand brief, so that from this point on nobody types a hex code
into a component again.

Nothing should look different on screen when this lands. This is scaffolding —
W38.1.2 is what actually moves the pixels.

## Background

TSA's brand brief asks for:

> The colors of the Thai flag (Dark blue, Crimson Red, White) along with Gold
> and Deep Green — colorful but not overwhelming, festive, clean.

What the codebase actually has is two separate systems fighting each other:

1. **`src/index.css`** defines a full shadcn token set — `--primary`,
   `--accent`, `--secondary`, and so on — where every single value is
   **greyscale** (`oklch(0.205 0 0)`, `oklch(0.97 0 0)`). Not one brand color is
   in there. The only brand-ish value is `--background: #f0ebe6`.
2. **The components** ignore those tokens and hardcode hex instead. Grep for
   `#` across `src/` and you'll find the brand applied by hand in at least eight
   places.

The result is drift. There are currently **three different reds** and **two
different navies** in use, and no rule saying which is correct:

| Hex | Where it's used | Note |
| --- | --- | --- |
| `#9B1B30` | `aero-hero-2.tsx`, `BoardMembersSection.tsx` buttons | The de-facto primary red |
| `#7A1028` | same files, hover state | Darker hover partner of the above |
| `#A51931` | `BoardMembersSection.tsx` name tags | The *official* Thai flag red |
| `#ED1C24` | `HomePage.tsx` menu, `BoardMembersSection.tsx` blob | A bright fire-engine red — noticeably off-brand next to the others |
| `#241D4F` | `UpcomingEvents.tsx`, `Footer.tsx`, menu | The de-facto navy |
| `#2D2A4A` | `BoardMembersSection.tsx` name tags | The *official* Thai flag blue |
| `#E8C547` | `aero-hero-2.tsx`, `HomePage.tsx` | Gold accent |
| `#FFFFF0` | several | Ivory, used as text on dark |
| `#141414` | `GalleryPage.tsx` | Near-black, used nowhere else |

Deep green — one of the five colors TSA explicitly asked for — **does not appear
anywhere on the site.**

Your job is to turn that mess into a ramp.

## Specification

1. **Add a raw brand palette** in the `:root` block of `src/index.css`, above
   the existing semantic tokens. Use a `--tsa-` prefix and a numeric weight
   scale so the palette reads as families rather than a list of one-offs.

   Start from these values. They reconcile the existing hexes into ramps and add
   the missing green:

   ```
   --tsa-navy-900   #1B1638   deepest ink — footer, gallery background
   --tsa-navy-700   #241D4F   primary navy surface (already the de-facto navy)
   --tsa-navy-500   #2D2A4A   official Thai flag blue
   --tsa-red-700    #7A1028   pressed / hover
   --tsa-red-600    #9B1B30   primary crimson
   --tsa-red-500    #A51931   official Thai flag red
   --tsa-gold-500   #E8C547   accent
   --tsa-gold-300   #F3DE97   soft gold — washes, borders
   --tsa-green-700  #1F5D4C   deep green
   --tsa-cream-100  #FFFFF0   ivory — text on dark surfaces
   --tsa-sand-100   #F0EBE6   page background (already in use)
   ```

   If you want to adjust a value, you may — but write a one-line comment saying
   why, and keep `--tsa-red-500` and `--tsa-navy-500` at the official flag
   values (`#A51931` and `#2D2A4A`, set by Thailand's 2017 royal decree). Those
   two are the ones a Thai student will recognize on sight.

2. **Note the `#ED1C24` problem in a comment.** That bright red is a genuine
   inconsistency, not a deliberate accent. Add a comment recording that it maps
   to `--tsa-red-500` and that W38.1.2 will replace it. Do not delete it yet.

3. **Rewire the existing semantic tokens** to point at the brand palette instead
   of greyscale. At minimum:

   - `--primary` → the crimson
   - `--primary-foreground` → cream
   - `--accent` → gold
   - `--background` → sand
   - `--foreground` → a near-black that is not pure `#000` (pure black on a warm
     sand background reads harsh — pick something with a hint of the navy in it)

   Leave `--destructive`, `--info`, `--success`, `--warning` alone. Those are
   status colors, not brand colors, and they should stay conventional.

4. **Add semantic surface tokens** for the three recurring section treatments so
   components stop reaching for raw palette values:

   ```
   --surface-navy        navy section background (Events, Footer)
   --surface-navy-fg     text on navy
   --surface-cream       cream card background (About cards)
   --surface-cream-fg    text on cream
   --surface-red         red card background (About cards)
   --surface-red-fg      text on red
   ```

5. **Expose everything to Tailwind.** This project is Tailwind v4, which uses
   the `@theme inline` block rather than a `tailwind.config.js`. Register the new
   tokens there so `bg-tsa-navy-700`, `text-tsa-gold-500` etc. become real
   utility classes. Follow the pattern already in the file — every existing
   `--color-*` entry in `@theme inline` is doing exactly this.

6. **Handle the `.dark` block.** It exists and is full of greyscale. The site
   does not currently offer a dark mode toggle and nothing sets the `.dark`
   class. Do **not** build dark mode in this spec. Either leave the block as-is
   with a comment saying it's unused pending a decision, or map it minimally to
   the navy family. Say which you chose in your PR description.

7. **Document the palette at the top of the file** in a comment block: what each
   family is for and, critically, **when not to use it**. Gold is an accent — if
   a later PR uses it as a background fill for a whole section, that comment is
   what the reviewer will point at.

## Acceptance Criteria

- [ ] The six `--surface-*` tokens exist

## Out of Scope

- Changing any file outside `src/index.css`
- Building a dark mode
- Removing hardcoded hex from components (that's W38.1.2)
- Fonts (that's W38.1.3)

## Hints

- Tailwind v4 has no config file. The theme lives in CSS via `@theme` /
  `@theme inline`. Read the existing `@theme inline` block before writing
  anything — it already shows you the exact pattern, and `--color-primary:
  var(--primary)` is the shape you're copying.
- The `inline` keyword matters. Look up what it changes about how the value is
  resolved before you decide whether new tokens go inside that block or in a
  plain `@theme` block.
- Existing values are a mix of hex and `oklch()`. Consistency is nice but not
  required; hex is fine and easier for the club to eyeball.
- To check a utility class really exists, open devtools and inspect an element
  you've applied it to. If the class is in the HTML but no CSS rule matches, the
  token isn't registered properly.
- The before/after screenshot check is the most valuable part of this spec. It's
  what catches the case where `--primary` was silently being used by a shadcn
  button somewhere you didn't look.
