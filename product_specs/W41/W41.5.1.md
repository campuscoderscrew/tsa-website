## Objective

Cut the three event videos from about 7 MB total to **under 2 MB total**. Keep
the same filenames so no code has to change, and keep the carousel looking the
same at the size it actually shows them.

## Background

The center card of the events carousel autoplays a muted, looping video. The
three videos add up to about **7 MB**. That's more than every other asset on
the site put together, and on a phone over cellular it's most of what a
visitor downloads. W41.2.2 left them out on purpose ("That's a separate
performance spec"). This is that spec.

The files are almost certainly sized for a phone camera, not a carousel card.
The card is a few hundred CSS pixels wide, so anything over 2× that size is
pixels nobody sees. They are also probably carrying things a muted background
loop doesn't need:

- an **audio track**. The video is muted, but the audio is still downloaded.
- a **high frame rate** (60 fps). The motion here is slow.
- **`moov` atom at the end of the file**. The browser can't start playing
  until it has downloaded the whole file. `-movflags +faststart` fixes that.

**Why this track doesn't touch code:** the videos are referenced from Track C's
files (`UpcomingEvents.tsx` today, `src/data/events.ts` after W41.3.2). If you
**replace each file in place with the same name**, nothing in Track C's code
has to change and there's nothing to conflict with. That rule shapes the whole
spec.

## Files You'll Touch

public/<event video 1>.mp4    replace (same filename)

Find the three filenames with `git grep -n "\.mp4" src/`. If W41.3.2 has
merged, they'll be in `src/data/events.ts`.

## Specification

1. **Measure first.** Before you change anything, record each video's:
   - file size
   - resolution, frame rate and duration
   - codec and whether it has an audio stream

   `ffprobe -v error -show_streams -show_format <file>` tells you all of it.
   Put a table in the PR. Also record the network panel's total transfer size
   for a cold load of the home page at 375px with "Fast 4G" throttling. Do it
   with the cache disabled.

2. **Work out the display size.** At 1440px and 375px, measure the center
   card's rendered width and height in devtools. Your target resolution is
   **2× the largest rendered size**, rounded to an even number (H.264 needs
   even dimensions). Keep the aspect ratio; don't crop.

3. **Re-encode.** Use H.264 in an `.mp4` container. Safari needs it, and it
   plays everywhere the site already works.
   - Scale to the size from step 2
   - Drop the audio stream (`-an`)
   - Use 30 fps, or 24 fps if it still looks smooth
   - Use `-pix_fmt yuv420p`. Without it, some encoders produce files Safari
     and Firefox won't play.
   - Use `-movflags +faststart`
   - Pick quality with `-crf`, not a fixed bitrate. Start at 28 and go up
     until you can see it get worse on the real card, then come back one or two
     steps.

   Write the command into `scripts/encode-video.sh`. It takes an input path
   and an output path. Add a comment that explains each flag in one line, and
   the CRF you settled on and why.

4. **Keep the loop clean.** If a video loops, check that the seam where it
   restarts isn't worse than before. Re-encoding can add a visible jump on the
   first frame. Watch at least three loops of each.

5. **Replace in place.** Overwrite each original with its re-encoded version
   under the **same filename**. Don't commit the originals anywhere in the
   repo. Git history still has them if anyone needs them.

6. **Check it actually plays.** Run `npm run build && npm run preview` and
   check autoplay on the center card in:
   - Chrome (desktop)
   - Safari (desktop or iOS)
   - a real phone, if anyone has one

   Then repeat the network measurement from step 1 and put before/after in the
   PR.

7. **Write down what you couldn't do.** Some wins need Track C's code. Don't
   make them; add them to `features_TODO.md` with your measurements:
   - a `poster` frame, so the card isn't blank while the video loads
   - `preload="none"` or `"metadata"` on videos that aren't on the center card
   - a WebM/AV1 `<source>` alongside the MP4, if the savings you measure are
     worth it

## Hints

- A starting point, which you should adjust rather than copy:
  `ffmpeg -i in.mp4 -vf "scale=-2:720,fps=30" -c:v libx264 -crf 28 -preset slow -pix_fmt yuv420p -an -movflags +faststart out.mp4`
  `scale=-2:720` means "720 tall, width to match, rounded to even".
- `-preset slow` makes encoding slower and the file smaller at the same quality.
  For three short clips it's worth it.
- Judge quality on the **card**, at the size it's shown, not full-screen in a
  video player. Artifacts you see full-screen are often invisible on a card.
- Browsers cache videos. Use a private window or "Disable cache" when you
  compare before and after.
- If W41.3.2 drops a video from the events data, you don't need to encode it.
  Check with Track C before you spend time on it.
