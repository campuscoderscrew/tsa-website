## Objective

Every pull request gets a Lighthouse report for the home page and the gallery.
A PR that makes the site noticeably heavier or less accessible gets flagged
before it merges, not discovered weeks later.

## Background

W41.2.3 makes lint and build a PR check, and lists Lighthouse CI under *Out of
Scope* as a "good idea" for `features_TODO.md`. This spec is that idea.

This week alone found three problems that a budget would have caught on the
day they were introduced:

- 7 MB of video on the home page (W41.5.1)
- a 428 KB logo shown at 72px (W41.2.2)
- a carousel no keyboard user could operate (W41.3.3). Lighthouse's
  accessibility audit can't catch everything, but it catches some of this
  class of problem.

The checks are automated, but **performance scores on CI runners are noisy**.
A shared GitHub runner's CPU varies from run to run, so the same commit can
score 78 one time and 88 the next. A budget that fails PRs at random gets
ignored or deleted within a week. The design job here is choosing what to
**fail** on, what to **warn** on, and how to make the numbers stable enough to
trust.

**There's a base-path trap.** Lighthouse CI can serve a folder itself
(`staticDistDir`), but it serves it at `/`. The built site expects to be under
`/tsa-website/`, so every asset 404s and the report is meaningless. You need
`npm run preview`, which honors the base path.

## Specification

1. **Get a baseline locally.** On `main` (after W41.5.1 and W41.5.2), run
   `npm run build && npm run preview`, then run Lighthouse CI against
   `http://localhost:4173/tsa-website/` and the gallery route, **5 runs each**.
   Record the median and the spread (min–max) for each category score, plus
   total byte weight. This baseline is what you set the budget from. Put it in
   the PR.

2. **Write `lighthouserc.json`:**
   - `collect`: `startServerCommand` running `npm run preview`, both URLs with
     the base path and the trailing-slash form W41.5.2 chose, and
     `numberOfRuns: 3`. LHCI asserts against the median run.
   - `assert`: choose per category and per audit. Defaults to start from, to
     adjust against your baseline:
     - **accessibility**: `error` below 0.9
     - **best-practices**, **seo**: `error` below 0.9
     - **performance**: `warn` only. Explain why in the PR, using the spread
       you measured.
     - **total byte weight** (`resource-summary` or `total-byte-weight`):
       `error` above your baseline + about 20%. Bytes don't depend on CPU
       noise the way scores do, so this is the performance check you can fail
       on.
   - `upload`: see step 4.

3. **Write `lighthouse.yml`.** It should match `ci.yml`'s conventions so the two read
   as a pair:
   - triggers on `pull_request` targeting `main`
   - installs exactly the way `deploy.yml` does (Node 22, npm cache,
     `npm ci --ignore-scripts`)
   - `npm run build`, then `npx lhci autorun`
   - `permissions: contents: read`
   - `concurrency` keyed on the PR, cancelling stale runs

4. **Decide where reports go.** You have two options:
   - `temporary-public-storage`: easiest, and gives a clickable link. But the
     report is **public** for about a week.
   - the `filesystem` target plus `actions/upload-artifact`: private to people
     with repo access, but they have to download a zip.

   The site is public, so the report doesn't leak much. Decide anyway, write
   one sentence on why, and make sure the report is reachable from the
   workflow run page either way.

5. **Prove it works.** On your PR:
   - link a green run
   - push a temporary commit that adds a large unused image to the home page
     (a few MB in `public/`, referenced with `BASE_URL`). Link the **red** run
     showing the byte budget fail, then revert it.
   - push a temporary commit that removes an `alt` or a button's accessible
     name. Link the run where accessibility drops, then revert.

6. **Advisory first, then required.** Don't ask for this to be a required
   check yet. Leave it advisory for **two weeks** so you can see whether it's
   flaky. Add a line to `features_TODO.md`, dated, saying when to revisit
   making it required, and what flake rate would block that.

7. **README.** Two sentences under the CI paragraph from W41.2.3: what the
   Lighthouse check does, and where to find the report on a PR.

## Acceptance Criteria

- [ ] Local baseline (median and spread, 5 runs, both pages) in the PR
- [ ] `lighthouserc.json` tests both pages **under `/tsa-website/`**; no 404s in the collected reports
- [ ] Accessibility, best-practices and SEO fail the check below their thresholds; performance score warns only; byte weight fails above budget
- [ ] Every threshold is justified from the baseline in the PR, not picked from a blog post
- [ ] `lighthouse.yml`: `pull_request` to `main`, same install as `deploy.yml`, `contents: read`, concurrency set
- [ ] Green run linked, plus a red byte-budget run and an accessibility-drop run, both reverted
- [ ] Report reachable from the workflow run page; storage decision written in the PR
- [ ] `ci.yml` and `deploy.yml` unchanged
- [ ] "Revisit making it required" entry in `features_TODO.md`
- [ ] README updated

## Out of Scope

- Making the check required (step 6 says when to revisit)
- Fixing whatever the first report finds. Write each finding into `features_TODO.md` with the file's owning track. Fixing them is next week's work.
- Testing pages behind interaction (an open lightbox, an open board overlay)
- Lighthouse on `deploy.yml` / the live site

## Hints

- `npx lhci autorun` runs collect, assert and upload in one go, reading
  `lighthouserc.json`.
- `startServerReadyPattern` tells LHCI what text in the preview server's output
  means "ready". Without it, the first run can hit a server that isn't
  listening yet.
- GitHub's `ubuntu-latest` runners already have Chrome. You don't need a step
  to install it.
- Lighthouse emulates a mid-range phone on a throttled connection by default.
  That's the right default for a student club site. Don't switch to desktop to
  make the numbers look better.
- If the performance score swings a lot, look at what moves first. The
  autoplaying video and any GSAP intro animation are the usual suspects for
  LCP and TBT variance.
- `"preset": "lighthouse:recommended"` asserts on every audit. It's far too
  noisy for a first budget. Start from explicit category thresholds.
