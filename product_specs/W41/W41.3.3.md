## Objective

Let someone who doesn't use a mouse or touchscreen browse every event, and
let a screen-reader user hear which event they're on.

## Background

`features_TODO.md` calls this "the most serious" accessibility issue on the
site, and that's accurate. The events carousel is **drag-only**:

- The cards have `onPointerDown` and nothing else. They aren't focusable, have
  no keyboard handler and no buttons.
- A keyboard user tabs straight past the section and **can't reach the second
  or third event by any means.**
- A screen reader hears the `aria-label` "Upcoming events carousel" on a
  `div`, then possibly a video, and no indication of how many events there are
  or which one is showing.
- The title and date under the cards animate in and out with
  `AnimatePresence`. They change visually but aren't announced.
- `prefers-reduced-motion` isn't handled. The fan swings on springs regardless.

The W3C's WAI-ARIA Authoring Practices has a **Carousel pattern** that
describes what this should be. Read it before writing any code. Most of this
spec is applying it.

## Specification

1. **Add previous / next buttons.** They must be real `<button>`s with
   accessible names ("Previous event" / "Next event"). They must be visible
   and usable on every viewport, and must sit outside the draggable area so a
   tap on them doesn't start a drag. Pressing one does exactly what a swipe
   does: same spring, same `slideDir`.

   Design them to match the section: navy surface, cream/gold, round. Put
   options in the PR with screenshots. 44×44px minimum touch target.

2. **Arrow keys.** When focus is inside the carousel region, <kbd>←</kbd> and
   <kbd>→</kbd> move between events. Don't hijack arrow keys anywhere else on
   the page.

3. **Structure and labels** per the APG carousel pattern:
   - the region has `aria-roledescription="carousel"` and a label
   - each slide has `role="group"`, `aria-roledescription="slide"`, and a
     label like "2 of 3: Water Festival"
   - non-center cards are hidden from assistive tech, so a screen reader only
     sees the active event
   - the event title and date/venue under the cards are in a **polite live
     region**, so moving to the next event announces it once

4. **Focus.** Visible focus ring on both buttons, using the brand gold so it
   shows on navy. Pressing next doesn't move focus off the button. That's
   expected, and it lets the user keep pressing.

5. **Reduced motion.** Under `prefers-reduced-motion: reduce`, changing event
   is an instant swap or a short opacity fade. No springs, no rotation. The
   title animation follows the same rule. Framer Motion has a hook for this.

6. **Video.** The center card autoplays a muted video. Make sure a
   screen-reader user isn't stuck inside a `<video>` with no label. Either
   label it or hide it from assistive tech, since the title is already
   announced. Choose and explain.

7. **Don't break drag.** Mouse drag and touch swipe must still work, including
   the "preview then snap back" behavior on a short drag.

## Acceptance Criteria

- [ ] Every event is reachable with the keyboard alone (Tab to the buttons, Enter/Space to advance), demonstrated in a screen recording
- [ ] ← / → work when focus is in the carousel and nowhere else
- [ ] Buttons are real `<button>`s, ≥ 44×44px, with accessible names and a visible gold focus ring
- [ ] Region, slides and live region match the APG carousel pattern; non-active cards hidden from assistive tech
- [ ] **Screen reader check** with VoiceOver (macOS <kbd>Cmd</kbd>+<kbd>F5</kbd>) or NVDA (Windows, free): write down in the PR exactly what was announced when you moved to the next event
- [ ] Reduced motion: no spring or rotation when changing events; recording with the setting on
- [ ] Drag and swipe still work on desktop and on a real phone
- [ ] Works with the one-event and empty states from W41.3.2. With one event, the buttons are hidden or disabled, not dead.
- [ ] Contrast of the buttons against navy meets WCAG AA for non-text UI (3:1)

## Out of Scope

- Auto-rotation. The carousel doesn't auto-advance, so there's no pause button to build. If you add auto-advance, the APG rules for a rotation control apply. Don't.
- Changing the fan design
- The events data

## Hints

- APG: search "WAI-ARIA Authoring Practices carousel". The "Tabbed" and
  "Basic" examples differ; Basic is the closer match here.
- `aria-hidden` on a subtree that contains a focusable element is a bug.
  Hidden cards must not contain anything tabbable. Check the `<video>`.
- `useReducedMotion()` from `framer-motion` returns a boolean you can branch
  on, both for the drag snap and for the title transition.
- Test the live region by actually listening. It's easy to announce twice
  (once from the label change, once from the live region) or not at all.
