## Objective

The board data can hold more than one year of officers without the home page
showing all of them, and there's a `/board` page ready to show any year. That's
the foundation for the **"Archive of Previous Board Members"** TSA asked for,
second on their list after the board gallery itself.

## Background

W38.3.1 moved the board into `src/data/board.ts` and gave every member a `term`
(`"2025-2026"`), with this note: "**Do not skip this** — the archive feature
needs it." The archive feature is this one.

Right now every entry in `BOARD_MEMBERS` is the current board, and
`BoardMembersSection.tsx` renders all of them. The moment anyone adds a past
board member to the file, that person appears on the home page as a current
officer. So the very first thing this spec does is make the home page show
**only the current term**, before any past data goes in.

How the site knows which term is "current" is a real decision:

- **Derived:** the latest `term` in the data. No extra field, but it means next
  year's board goes live the moment someone adds the first new entry, even
  half-entered with photos missing.
- **Explicit:** a `CURRENT_TERM` constant an officer changes on purpose when the
  new board is ready. One more thing to remember, but nothing goes public by
  accident.

TSA also hasn't given us past boards yet (`features_TODO.md`, open question 7).
This spec builds the structure and asks for the data. It must not invent any.

## Specification

1. **Decide how the current term is chosen** (see Background). Write the
   decision and the reason in a comment at the top of `board.ts` and in the PR.
   Whichever you pick, the rule lives in **one place**.

2. **Export helpers from `board.ts`:**
   - the current term
   - every term that has members, newest first
   - the members of a given term

   Components use these helpers, not the raw array. W42.3.2 (hero avatars) will
   import the current-term helper too, so name it clearly and post the name in
   the group chat when it merges.

3. **Filter the home page.** `BoardMembersSection` renders only the current
   term's members. With today's data this changes nothing on screen. Prove it
   with a before/after screenshot. Then prove the filter works: temporarily add
   a fake past-term entry, confirm it doesn't appear on the home page, and
   remove it before you commit.

4. **Decide whether `photo` stays required.** Past members may not have a usable
   photo. If you make it optional, TypeScript must then force every component
   that renders a photo to handle the missing case, including the home card. If
   you keep it required, say what an officer does for a past member with no
   photo. Explain your call in the PR. W42.2.2 builds the visual fallback either
   way.

5. **Create `/board`.** Register the route (one line in `App.tsx`, Track E's
   file). The page follows this week's page conventions (one `<h1>`,
   `<main id="main-content" tabIndex={-1}>`, title
   `Board · Thai Student Association at UMD`) and, for now, lists the current
   term's members by name and role. W42.2.2 turns that into the real archive
   layout. Use the brand header pattern (eyebrow, divider, heading).

6. **Link to it from the home section.** Add a "Meet past boards" (or similar)
   link under the home board grid. It goes through the router, not a plain
   `href` (see this week's README).

7. **Ask the club for past boards.** Send Alison Wang
   (awang527@terpmail.umd.edu) a short message asking for names, roles,
   majors and photos of previous boards, by school year, and whether each person
   is OK being listed. Paste the message in the PR. If you get answers this
   week, add only what was confirmed. If you don't, the page ships with the
   current term and an honest note that past boards are coming.

## Hints

- If term strings are always `"YYYY-YYYY"`, a plain string sort orders them
  correctly. Write that assumption down; W42.2.3 will enforce it.
- The W38.3.1 hints still apply: GitHub Pages is case-sensitive, and
  `Alison.jpg` is not `alison.jpg`.
- Testing a filter by temporarily adding data is fine. Committing that data is
  not. Check your diff before pushing.
- React 19 lets you render `<title>` inside a component. Check the version in
  `package.json` first.
