## Objective

The events page also shows what TSA has already done: past events grouped by
school year ("2025–2026") and semester, most recent first, filterable by
category. That's the **"archive of previous events"** TSA asked for, and it
lets a prospective member see that the club is active.

## Background

TSA's intake form asks for an **"Archive of Previous Board Members & Events."**
W41.3.2 added a past-events helper to `src/data/events.ts`, and W42.1.1 built
an `EventAgenda` component that takes any list of events. Nothing shows past
events yet.

How you group them matters. A club thinks in **school years and semesters**,
not calendar years: Senior Send-Off in December 2025 and Water Festival in April
2026 belong to the same year of the club, under the same board. W38.3.1 gave
every board member a `term` like `"2025-2026"` for exactly this reason. If
events use the same school-year label, a future spec can show "the 2025–2026
board ran these events" with no new data.

UMD's semesters run roughly late August to mid December (fall) and late January
to mid May (spring), with winter and summer sessions in between. A month-based
rule is good enough. You don't need the registrar's exact dates.

## Specification

1. **Add school-year helpers to `events.ts`.**
   - one that takes an event and returns its school year in the board's
     `term` format (`"2025-2026"`)
   - one that returns its semester (`"Fall 2025"`, `"Spring 2026"`)
   - one that groups past events by school year, most recent year first, and
     by semester inside each year

   Write down your month rule in a comment at the top of the helpers (which
   months are fall, which are spring, and what you do with summer and winter
   events). Use the same format as `term` in `src/data/board.ts`: if that file
   uses a hyphen, so do you.

2. **Show past events on the events page.** Below the upcoming agenda, add a
   "Past events" section with a heading per school year and a sub-heading per
   semester. Reuse `EventAgenda` for each group. Past events should look
   clearly *past*: quieter styling is fine, but text must still meet AA.

3. **Decide how to switch between upcoming and past.** Two reasonable shapes:
   - one long page: upcoming at the top, archive below
   - two views ("Upcoming" / "Past") switched by a control, with the choice in
     the URL (`/events?view=past`) so it can be linked

   Pick one and say why in the PR. If you build the switch, it must be real
   buttons or links with the current state exposed (`aria-pressed` or
   `aria-current`), and the URL must survive a refresh.

4. **Add a category filter.** `TsaEvent.category` is a small union (W41.3.2).
   Build `EventFilters`: "All" plus one option per category, applied to both
   upcoming and past. Put the active filter in the URL too
   (`?category=festival`). An unknown value in the URL falls back to "All"
   instead of showing nothing.

5. **Announce filter results.** When the filter changes, a screen-reader user
   should hear how many events are now showing ("4 events"), once. Use a polite
   live region.

6. **Keep "today" a runtime value.** Whether an event is past is decided in the
   visitor's browser when the page loads, not at build time. Your grouping must
   call the existing upcoming/past helpers, not a date you computed somewhere
   else.

## Acceptance Criteria

- [ ] Past events are grouped by school year (newest first) and then by semester
- [ ] The school-year label matches the `term` format used in `src/data/board.ts`
- [ ] A December 2025 event and an April 2026 event land in the same school year; a September 2026 event does not
- [ ] The month rule is documented in a comment in `events.ts`
- [ ] Upcoming/past layout decision explained in the PR; if it's a switch, its state is in the URL and survives refresh
- [ ] Category filter works for both upcoming and past; its state is in the URL; an invalid URL value falls back to "All"

## Hints

- Write the school-year rule as a small pure function and try it by hand on the
  edge months (January, May, June, August, December) before you wire it in.
- Avoid `new Date("2026-04-18")` for month extraction; that's parsed as UTC
  midnight and can roll back a day in Eastern time. For a date-only ISO string,
  slicing the year and month out of the string is the safest option.
- react-router's `useSearchParams` reads and writes query parameters without a
  full navigation.
- Read the WAI-ARIA Authoring Practices on the **toolbar** and **button**
  patterns before building a row of filter buttons. A native `<select>` is also
  a perfectly good answer.
