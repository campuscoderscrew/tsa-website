## Objective

The "Community" avatar stack in the hero shows real TSA members, or is removed,
instead of four strangers from a stock-photo site. The hero also stops depending
on a third-party image server for its first paint.

## Background

`src/components/ui/aero-hero-2.tsx` renders four avatars next to the word
"Community". They're loaded from **Unsplash URLs**: photographs of random people
who have nothing to do with TSA, presented as if they're members.
`features_TODO.md` calls it out under "Content that's currently fake."

It's a problem on two fronts:

- **Honesty.** The hero is the first thing every visitor sees, mostly arriving
  from TSA's Instagram, where they know what members look like.
- **Performance.** Four images from another domain in the hero mean an extra
  connection and download before the first screen settles, outside our control.

The obvious replacement is the current board: real people who already agreed to
be on the site (W38.3.1). But the board photos in `public/` are full-size
JPEGs. Four of them in a 40px avatar stack would download far more bytes than
the stock images did, which would make the hero *slower*.

The avatar fallback in the hero already uses the brand navy (W38.1.2 folded a
stray `#1C2B5A` into the token), so the component already supports showing
initials when an image is missing.

## Specification

1. **Decide: real members or remove.** Ask the club (Alison Wang,
   awang527@terpmail.umd.edu) which they prefer, and whether the board members
   pictured are OK appearing in the hero specifically, not just in the board
   section. If you can't get an answer this week, **remove** the stack: no
   avatars is better than fake ones. Say which you shipped and why in the PR.

2. **If using members, take them from the data.** Import the current board
   from `src/data/board.ts` (through W42.2.1's helper if it has merged). Don't
   hardcode names or filenames in the hero. Pick which members show with a
   simple, stable rule (the first four in board order is fine; random is not,
   because the hero would change on every load and every re-render).

3. **Make small copies.** For each photo the hero uses, create a square copy in
   `public/avatars/` at 2× the largest rendered avatar size, compressed. Use the
   same filename as the board photo (exact case) so the hero can derive the
   avatar path from the board data with no new field. Record the dimensions and
   file sizes, before and after, in the PR.

4. **Reference them the way the build check expects.** Use
   `` `${import.meta.env.BASE_URL}avatars/${photo}` `` so W41.2.2's asset check
   and W42.2.3's data check both apply.

5. **Make the label honest.** If the stack shows board members, the text next to
   it should say so (or say something true, like "Meet the board"), and could
   link to the board section. If the stack is removed, remove or rewrite the
   label so the layout doesn't leave a gap.

6. **Alt text and fallback.** Avatars of named people get alt text with the
   name. Alternatively, if the group has a visible label that already names
   them, mark the individual images decorative and give the group one
   accessible name; pick one, not both. Keep the initials fallback for a photo
   that fails to load.

7. **Remove the external dependency completely.** No `images.unsplash.com` (or
   any other external image host) left in the hero, and no `preconnect` hint
   for it in `index.html`. If there is one there, tell Track E; it's their file.

## Hints

- Squoosh (squoosh.app) can resize and compress one image at a time in the
  browser. `sips` on macOS or ImageMagick's `magick` can do several from the
  command line.
- Measure the rendered avatar size in devtools before choosing the export size.
  A 40px avatar needs an 80×80 image, not 512×512.
- Crop square around the face. A board photo cropped from the center may cut the
  person off.
- If the hero is a link to the board section, that section's anchor must exist on
  the page the link is on. Test it from the built site.
